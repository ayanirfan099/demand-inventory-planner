# Synthetic smoke run (not a benchmark)

`scripts/smoke_study.py` runs the full study protocol on the **deterministic synthetic
dataset** that the demo seeder also uses. It exists to prove the pipeline runs end to end and
to give a reviewer a fixed output to compare against after a change.

Read the heading literally:

> This is not a benchmark. The data is generated by `forecastops_forecasting.generator`, on one
> split, with one seed. Nothing here says how the model behaves on real retail demand, and no
> number on this page should be quoted as a performance claim.

## Reproduce

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements/dev.txt
python scripts/smoke_study.py
```

## How to read it

1. **Selection and reporting disagree here, and that is the point.** Rolling-origin validation
   picked the baseline; the chronological holdout preferred gradient boosting (WAPE 0.192 vs
   0.230, i.e. 0.836× the baseline). Because the holdout never influences selection, the
   product reports both facts instead of quietly picking the flattering one. A tool that
   selected on the holdout would have shipped GBM and claimed a 16% improvement it cannot
   justify.
2. **Bias is positive for both models** (+1.1 to +1.4 units/day). The generator has a mild
   growth trend, so models trained mainly on earlier data under-predict the end of the series.
   A planner should see that sign rather than a single "accuracy" score.
3. **Cold brew is the weak series** across stores (~0.40–0.43 WAPE): it is the noisiest series
   in the generator. Aggregate metrics alone would have hidden this; the per-series table is
   why the UI always shows both.
4. **Runtime** (~4 s for 12 series × 365 days, 2 folds, 2 models) is the reason the per-job
   wall-clock budget defaults to 300 s: a 200-series dataset is ~16× the work.

## What this does not cover

- Real seasonality, promotions, prices, holidays, stockouts or censored demand.
- Multiple datasets, multiple seeds, or any statistical significance claim.
- Memory profiling, concurrency, or behaviour on PostgreSQL versus SQLite.
- Any comparison against published forecasting benchmarks or other libraries.

For those, you would need real data you are allowed to use and a separate evaluation design —
neither of which this repository ships.
