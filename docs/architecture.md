# Architecture

ForecastOps is a small monorepo with four deployable pieces and one shared library. The
guiding rule: **the forecasting library knows nothing about HTTP or SQL**, so it can be
tested, profiled and reused without a database.

```
apps/web (Next.js 15, RSC + client components)
   │  browser → web origin only: /api/* and /healthz are proxied by next.config.mjs
   ▼
services/api (FastAPI)
   │  ├── deps.py            session → AuthContext (user, org, role)
   │  ├── routers/*          thin HTTP layer, no business rules
   │  ├── services/*         ingestion, runner, inventory, alerts, exports, queue, storage
   │  ├── models.py          SQLAlchemy 2.0 typed models
   │  └── migrations/        Alembic (single initial revision, autogenerated then reviewed)
   ▼
PostgreSQL 16 (SQLite for local/tests)      Redis 7 (job queue, optional)
   ▲
   │  claim → run → write, always by job id
services/worker (RQ worker or DB poller) ──▶ packages/forecasting (pandas/sklearn)
```

## 1. Components

| Component | Responsibility | Deliberately not responsible for |
| --- | --- | --- |
| `apps/web` | Rendering, navigation, form state, charts, textual chart equivalents | Business rules, authorization, metric math |
| `services/api` | Auth, tenancy, validation, orchestration, persistence, exports | Model training details, chart layout |
| `services/worker` | Executing claimed jobs out of band | Accepting requests |
| `packages/forecasting` | Validation → feature build → study → metrics | Knowing that a database exists |
| `packages/contracts` | Shared constants (error codes, limits, alert rules, metric names) + drift tests | Runtime behaviour |

## 2. Request flow (a forecast run)

1. `POST /api/v1/forecast-jobs` with a dataset id, horizon, holdout, folds, models and an
   optional `idempotency_key`.
2. `deps.require_role("analyst")` resolves the session cookie → `AuthContext`
   (user + active org + role). Every subsequent lookup is filtered by `org_id`.
3. The router validates bounds (horizon ≤ 90, holdout 7–90, folds 0–5, known model keys,
   baseline auto-inserted if omitted) and rate-limits the caller.
4. A `ForecastJob` row is created in `queued` state. A repeat request with the same
   idempotency key returns the existing job with `idempotentReplay: true` instead of a
   second unit of work.
5. `queue.dispatch` hands the job to the configured executor (see §3).
6. The worker claims the job atomically (`UPDATE ... WHERE status='queued'`), writes
   `status='running'`, `stage`, `progress`, then runs the study with a progress callback
   that doubles as a cancellation check and a wall-clock budget check.
7. Results are persisted: one `ForecastRun` per model, `ForecastPoint`s, `MetricResult`s
   (aggregate with `series_id = NULL`, plus one row per series), alerts are evaluated,
   and `status='succeeded'`.
8. The UI polls the job, then renders the run: metrics, holdout vs actual chart, per-series
   table, residuals, exports.

### Tables

`users`, `organizations`, `memberships`, `sessions`, `datasets`, `dataset_versions`,
`series_definitions`, `actual_observations`, `model_configurations`, `forecast_jobs`,
`forecast_runs`, `forecast_points`, `metric_results`, `inventory_policies`,
`reorder_suggestions`, `alerts`, `report_exports`, `audit_events`.

Every business table carries `org_id` (directly or through its parent) and every query
funnels through `deps.get_*` helpers that filter by the caller's org. Cross-tenant access
returns **404**, not 403: a tenant should not learn that another tenant's id exists.

## 3. Job execution modes

`FORECASTOPS_EXECUTION_MODE` picks the transport, and the same `run_forecast_job(job_id)`
function runs in all three. This is why local development, tests and production share one
code path.

| Mode | How work is handed off | Used for |
| --- | --- | --- |
| `thread` | Bounded `ThreadPoolExecutor(max_workers=2)` inside the API process | Local dev, hosted preview, tests |
| `rq` | `Queue(...).enqueue(run_forecast_job, job_id, job_timeout=...)` | Docker Compose / production |
| `external` | Nothing is dispatched; the job stays `queued` | Standalone poller worker (`worker.poll`) |

The DB-poller worker claims with a conditional `UPDATE` so two pollers cannot both run the
same job, recovers abandoned claims on start (`sweep_stale_claims`), sweeps expired previews,
and exits cleanly on SIGTERM. Both the claim and the recovery are covered by
`tests/test_worker_poll.py`.

**Queue failure is visible, not silent.** If Redis is unreachable at enqueue time, the job
is marked `failed` with `failure_code = "queue_unavailable"`, an alert is raised, and the
API returns the failure. The product never claims a job is scheduled when it is not.

Failure codes: `queue_unavailable`, `timeout`, `invalid_dataset`, `dataset_unavailable`,
`worker_error` (plus model/study codes such as `insufficient_history`, `model_failure`).

## 4. Storage layout

Uploaded and normalised data lives on disk, keyed by tenant and version, and the database
stores only metadata plus a content fingerprint:

```
data/datasets/{org_id}/{dataset_id}/v{n}-{fingerprint12}.csv
```

- Fingerprint: `sha256:<canonical csv>`, so re-importing the same file is detected and the
  existing version is reused (`created=False`) instead of duplicating rows.
- Uploaded bytes are parsed once into a frame; the stored artefact is the canonical CSV,
  not the original file, so a downstream reader cannot be surprised by encoding or column
  order.
- Uploads are previewed first: `POST /datasets/previews` writes a temporary preview and
  returns a rejection report; `POST /datasets/imports` commits. Stale previews are swept on
  API startup.

## 5. Security model

- **Sessions**: random token in an `HttpOnly`, `SameSite=Lax` cookie; only the SHA-256 hash
  is stored, so a database leak does not hand out live sessions. 12-hour TTL, refreshed
  `last_seen_at`, absolute expiry enforced on every request.
- **Roles**: `owner > analyst > viewer` via `require_role(minimum)`; authorization is
  centralized in `deps.py`, not sprinkled through handlers. Owners additionally manage
  memberships and can read the audit log.
- **CSRF**: `SameSite=Lax` plus an origin check middleware that rejects unsafe methods from
  an unknown `Origin` (403 `origin_not_allowed`). Requests with no `Origin` header (curl,
  server-to-server) are allowed because they cannot carry a victim's ambient cookie.
- **CORS**: explicit allow-list from `FORECASTOPS_ALLOWED_ORIGINS`, credentials enabled,
  headers limited to `content-type`, `x-request-id`, `x-idempotency-key`.
- **Uploads**: size cap checked while streaming, row/series caps, extension and content-type
  checks, stored under a generated name (never the client's), and never executed.
- **Errors**: RFC-shaped `{"error": {"code", "message", "request_id"}}`; messages never
  contain stack traces, SQL or filesystem paths.
- **Secrets**: `.env` is git-ignored; only `.env.example` is committed, with fictional demo
  values.

## 6. Observability

- Structured logs with a `request_id` on every request (echoed as `X-Request-Id`) and a
  `job_id` for everything a worker does; both are attached via context variables so
  library code does not need to pass them around.
- `GET /healthz` — liveness only, no dependencies (safe for container restarts).
- `GET /readyz` — database round-trip, writable data directory, and queue mode/Redis state;
  returns 503 when a hard dependency is down and reports `degraded: true` when Redis is
  missing but the API can still serve reads.
- `ForecastJob.request_id` links an async unit of work back to the HTTP request that
  created it.
- Every consequential action writes an `audit_events` row: login, dataset import, job
  create/cancel/retry, policy change, suggestion status change, export.

## 7. Frontend architecture

- Next.js App Router with a route group `(app)` for the authenticated shell and a
  standalone `/login`. Only `/` is a server component (a redirect to `/dashboard`).
- The shell is a client component: it resolves the session via `/api/v1/auth/me`, bounces to
  `/login` on 401, then renders navigation filtered by role. Each page fetches its own data
  through the same-origin `/api/*` proxy, so cookies stay first-party and there is exactly one
  data-access path. Trade-off: a loading state and a JavaScript requirement for the UI, stated
  in a `<noscript>` notice; the REST API is usable without a browser.
- `SessionProvider` holds the current user/org/role for the shell; a 401 anywhere bounces
  to `/login?next=…`.
- Charts are Recharts components wrapped by `charts.tsx`, which always renders a
  `chartSummary` text alternative and an `sr-only` table-equivalent description; colour
  choices are colour-blind-safe (blue/teal/amber/vermillion, Okabe–Ito based) and never the
  only encoding of a series.
- Design: light neutral canvas, dense tabular layouts, blue/teal accents — an admin tool,
  not a marketing page. All motion respects `prefers-reduced-motion`; focus states are
  visible; every control is reachable by keyboard.
- Accessibility is asserted, not assumed: `apps/web/tests/contrast.test.ts` reads the palette
  tokens out of `globals.css` and fails when a text/background pair drops below WCAG AA
  (4.5:1, or 3:1 for large text). Finding real failures is the point — the first run caught
  teal badges at 4.22:1, amber badges at 4.15:1, muted ink at 4.48:1 on the deepest canvas
  and faint ink at 2.72:1, all of which were darkened to pass. There is no automated axe audit;
  the claim here is contrast plus keyboard-first markup plus textual chart equivalents, no more.

## 8. Failure behaviour

| Failure | Behaviour |
| --- | --- |
| Redis down (`rq` mode) | Job fails fast with `queue_unavailable` + alert; reads continue working |
| Worker dies mid-job | The poller's startup sweep marks `running` claims older than the budget + 60 s as `failed` (`worker_error`) with one audit event and one alert; retry is an explicit user action, never automatic |
| Timeout | Progress callback aborts the study, job fails with `timeout`, partial results are not persisted |
| Database down | `/readyz` → 503; data endpoints return 503 `service_unavailable` with no driver detail in the body (the session lookup is the first query, so an unauthenticated request still gets 401); covered by `tests/test_resilience.py` |
| Dataset file missing | Job fails with `dataset_unavailable` (never an empty forecast) |
| Invalid upload | Rejected with row-level reasons; nothing committed |
| Stale preview | `preview_expired`, user re-uploads |

## 9. Deployment

`infra/docker-compose.yml` runs Postgres 16, Redis 7, the API (which applies Alembic
migrations on start), an RQ worker and the Next.js app, with a shared `data` volume. Health
checks gate startup. Seeding is an explicit one-off command, never a startup side effect.

CI builds all three images, validates the compose file, and starts the API image for real: it
must migrate, then answer `/healthz` and `/readyz`. The live queue is exercised against a Redis
7 service container. Neither is claimed on the strength of a code review.

See [`operations.md`](operations.md) for limits, retention, backups and the runbook, and
[`adr/`](adr) for the decisions behind these choices.
